# INSTALLER-STANDARD — The Mandatory Web Installer Standard for Every New SOFI Project

> **Status:** binding standard — mandatory on every web project SOFI produces, without exception.
> **Authority:** owner order `OWNER-DIRECTIVE-2026-0823`.
> **Execution owner:** `bck-blade-engineer` (room 05) within phase S4.

## | 1. Purpose & Authority

1. Unify the `/install` wizard across every new web project: the client receives a system they launch step by step from the browser, never touching a command line.
2. Secure the most dangerous moment in any system's life — first-time initialization (secrets, database, admin account) — with strict, non-negotiable controls.
3. This standard is issued by owner order `OWNER-DIRECTIVE-2026-0823`; any violation is treated as a breach of production-gateway security and escalated immediately to `brd-ceo`.

## | 2. Scope

1. Applies to every web project generated by `sofi-project-spawn` on the **Laravel API + Flutter/Dart interface** stack (v2 program — comprehensive design-first).
2. The `/install` wizard is an integral part of phase **S4** (build): `bck-blade-engineer` builds it fully before any delivery.
3. S4 cannot close, nor can the project cross the quality gate (S6), before the installer passes the Section 6 tests.
4. The wizard's life ends by writing `install.lock` — later updates never pass through it again, and the lock is final and never lifted.

## | 3. Wizard Stages (0 ← 6)

### Stage 0 — Welcome & Project Name
- A welcome screen explaining what will happen in simple steps and asking only for the project name.
- The entered value feeds `APP_NAME` in `.env` and becomes the panel title in the interface.

### Stage 1 — Requirements Check (PASS/FAIL)
- A check table itemizing each requirement: pass ✅ or fail ❌, plus a **re-check** button after fixing any item.
- Mandatory items:
  - PHP ≥ 8.2.
  - Mandatory PHP extensions — each as its own row in the check table:
    - `pdo_mysql` or `pgsql`
    - `mbstring`
    - `openssl`
    - `ctype`
    - `json`
    - `bcmath`
    - `curl`
    - `dom`
    - `fileinfo`
    - `tokenizer`
    - `xml`
  - Composer ≥ 2 · Node ≥ 20.
  - An actual database connection (a real test, not an assumption).
  - Write permission in `storage/` and `bootstrap/cache`.
- The "Next" button stays disabled while any single item is FAIL.

### Stage 2 — Database Credentials
- Fields: type (MySQL/PostgreSQL), host, port, database name, user, password.
- **A real connection test** before proceeding is allowed — connection success is the condition for enabling "Next".
- Connection failure shows a simplified cause in user language (wrong host, rejected password…) rather than a raw exception message.

### Stage 3 — Generating `.env`
- Generate the `.env` file automatically from the project template, filling in the values gathered from earlier stages.
- `APP_KEY` is generated automatically (`php artisan key:generate`) with zero manual intervention.
- Secrets (keys and passwords) are **shown once only** at save time and never reappear on screen or in logs afterwards.
- File permissions after writing: `0640` for the file, owned solely by the web service user — no world-readable access.

### Stage 4 — Running Migrations & Seeders
- Execute migrations and seeders through a step-by-step queue with a visible **progress bar**.
- Every step is recorded in a **verifiable log** (operation name, timing, result) that the user can expand and read.
- Any failure halts the process immediately and presents a human message with a "retry" option for the failed step alone.

### Stage 5 — Admin Account
- Fields: admin name, administrative email in valid format (real format validation), password, password confirmation.
- Password policy: **≥ 12 characters** including letters, numbers, and symbols — validation is enforced server-side, not in the UI alone.
- The password is entered **twice** (field + confirmation) and both must match.
- Storage uses `Hash::make` encryption only — no plaintext storage in any form.

### Stage 6 — Final Lock
- Writing the `install.lock` file at the project root — the sole recognized mark of completed installation.
- The `InstallGuard` middleware on `/install` routes: once the lock exists, any request gets **403** and the user is redirected to login.
- The lock is final: no interface and no command reopens the wizard after completion; reinstalling means a brand-new project from scratch.

### General Rules Governing All Stages
- A stage bar atop every screen shows where the user stands (0 ← 6) and the current stage.
- Backward navigation between stages is allowed only before locking, without losing previously entered data.
- Wizard state persists in the session; a dropped connection returns the user to the last completed step.
- No "Next" button until the stage's condition is fully satisfied — jumping stages is forbidden.
- Inputs from sensitive stages (database passwords) do not linger in the session after leaving them.

## | 4. Strict Security Rules

1. **CSRF** in every form inside the wizard without exception (`@csrf` / token on every POST).
2. **Rate-limit of 10/min/IP** on all installation routes (`throttle:10,1`) to repel guessing and automated attacks.
3. **`APP_DEBUG=false` always** — no exception in any environment, and no stack trace ever shown to the user.
4. **No secrets after save:** no secret on screen, in a log, or in a JSON response beyond the moment of its first display — shown once, then permanently erased.
5. User input is always validated server-side; UI validation is cosmetic and never a substitute.
6. Installation routes operate only while `install.lock` does not exist — the guard checks the lock before processing any request.
7. No secret is stored in session files or on-disk cache beyond the moment of use.

## | 5. User Experience (UX)

1. **Arabic RTL first**: page direction, alignment, and fields are Arabic from the very first screen.
2. **S3 tokens exclusively**: colors, fonts, and spacing from the approved design system via the Design Freeze Review (DFR) gate (phase S3) — no improvised colors.
3. **Heroicons outline icons** exclusively, uniform size and scale across the wizard.
4. **Non-technical human messages** (Law 11): every failure explains "what happened" and "what to do now" in the user's language — an unexplained technical term = a violation.
5. **A closing success state:** a completion screen congratulating the user and clearly stating the **next step** (logging in with the created email, and where to find the panel).
6. **A loading state per operation:** buttons disable during checks and execution and reject double clicks.
7. **Screen consistency:** identical element order and spacing across all stages, with the stage bar always visible.

## | 6. Testing in S6

1. **The full clean-install scenario:** empty environment → crossing stages 0←6 completely → successful login with the generated admin account → `install.lock` present.
2. **The post-lock scenario:** attempting to open `/install` after lock **must fail** (403 + redirect to login) — any success = gate failure and delivery rejection.
3. Both scenarios' results are documented with evidence (screenshots + exit codes) inside the S6 package (the shield) before any delivery.
4. Mandatory negative scenarios are also tested:
   - Wrong database credentials → stage 2 refuses to proceed with a human message.
   - A password under 12 characters or lacking symbols → stage 5 refuses to save.
   - A form without a CSRF token → the request is rejected.
   - Exceeding the 10 requests/minute limit → a temporary 429 response.

## | 7. DO / DON'T Table

| ✅ Do | ❌ Don't |
|---------|-----------|
| Actually test the database connection before proceeding | trust inputs without testing |
| Generate `APP_KEY` automatically | ask the user to paste a key manually |
| Show secrets once then erase them | re-display a secret or write it to a log |
| Enforce passwords ≥12 characters server-side | rely on UI-only validation |
| Encrypt the admin password with `Hash::make` | store any password as plaintext |
| Lock `/install` permanently with `InstallGuard` | leave the wizard accessible after installation |
| Human failure messages with suggested fixes | throw raw exceptions or use abstract jargon |
| Build the UI with S3 tokens and RTL | improvised colors/fonts and LTR |
